2009年のiMacにOmarchyを入れる

標準のOmarchy 4.5.0インストーラーを2009年のiMacで起動すると、内蔵画面に同じロゴが2×2で並び、表示が崩れた。そこで公式ISOの起動構造を保ったまま、Radeonの修正を組み込んだ専用ISOを作った。下の2枚は、その標準ISOの起動時と、改修版R2で導入したあとのデスクトップ。

  • iMac10,1
  • 21.5インチ / Late 2009
  • Core 2 Duo 3.06 GHz / 4 GB
  • Radeon HD 4670
iMac専用ISOをどう作ったか修正の出自と、今回作った部分Radeonと内蔵画面macOS High Sierra を残して内蔵ディスクを分割同じSD、違うリーダー電源投入からログイン画面までChromiumの描き残しCore 2 Duo での H.264 動画再生4.6 RC1 に向けたカーネル試験実機の設定と開発環境Codex CLIとデスクトップアプリパッチとビルド設定参考・追記履歴

iMac専用ISOをどう作ったか

1. 公式ISOを出発点にした。 署名と公開SHA-256を照合した omarchy-4.5.0-x86.iso を使い、ISOとライブ環境のSquashFSを読み取り専用で展開した。カーネル本体 linux-omarchy 7.2.15-1 は公式のまま。OS全体の再ビルドはしていない。

2. Apple Silicon上でx86_64の部品だけをビルドした。 ColimaのLinux VM上で、QEMUの命令変換を使い、Dockerの linux/amd64 Archコンテナを動かした。署名を確認した公式カーネルのヘッダーと対応するGCC 16.2.1で、内蔵パネルのタイミングを補正する radeon.ko だけを再ビルド。モジュールの互換性情報と依存関係を確認し、omarchy-imac10-1-radeon 7.2.15-1 にパッケージ化した。HyprlandはArchのビルドレシピを元に、ウィンドウ枠シェーダーの discard を透明描画（alpha 0）に替える限定パッチを当てて 0.56.2-4.1 にした。両パッケージは公式署名とは別の鍵で署名した。

3. ライブ起動とインストール後の両方に修正を入れた。 GRUBに iMac10,1 でだけ表示される専用起動項目を追加し、修正版Radeon入りのライブ環境と mkinitcpio で作った初期起動イメージを使うようにした。専用経路ではパーティション変更前にパッケージ署名を確認。インストール時に一時キーリングと pacman -U で修正版を導入し、Radeonモジュールの読み込み優先順位も確認した。既製の統合カーネルイメージ（UKI）は流用せず、通常のLimine用の流れで再生成させた。公式のインストール元 omarchy-root.img.zst 自体は変更していない。

4. 公式の起動構造を保ってISOに戻した。 mksquashfs でライブ環境 airootfs.sfs をZstandard圧縮し、SHA-512の照合ファイルを作り直した。xorriso -boot_image any replay でGRUB設定、初期起動イメージ、SquashFSとハッシュを差し替え、元のISOの起動構造を引き継いだ。

5. VMで検証し、実機で確かめた。 公式ISOがVMでインストーラーまで進むことを確認。Radeon修正だけを入れたR1ではインストーラーのパス判定の不具合を見つけ、R2で修正した。R2は再マウントして公式カーネルがバイト単位で同じこと、修正版モジュール、ハッシュと署名を確認。UEFI・Core 2 Duo相当・4 GBのVMで暗号化インストールを完了し、仮想インストール媒体を外して起動、導入後のUKIも確認した。ただしVMの描画はソフトウェアの llvmpipe。Radeon実機での表示・起動・Wi-Fiの確認とは分けている。 導入後の VM では Hyprland にログインし、Foot の同じウィンドウを別ワークスペースと別の画面座標に移動できた。

成果物： omarchy-4.5.0-imac10-1-r2-x86.iso（6,689,390,592バイト）
SHA-256: 9a5b450eb67ccf4d3de2a385a52f7755ca4fed552928b298d420f70e649ddbc7
検証したイメージの識別情報で、このページからISOを配布しているわけではない。

修正の出自と、今回作った部分

土台：Omarchy公式。 起動メディアのベースはOmarchy公式4.5.0のx86版。インストーラー側は公式omarchy-isoの参照ソースと、ISO内の該当ファイル2点のハッシュを照合した。この参照コミットがISOに記録されていたわけではない。カーネル本体と圧縮されたインストール元イメージは公式配布物のまま。

採用したRadeon修正：choyerのリポジトリ。 patches/panel-encoder-combined.patch を、参照コミット 0d5a406a312eb91c640c6137ef4e90813baa8778 から変更せずに採用。iMac10,1の対象パネルに限り、ビデオBIOSのパネル表のメモリ上のコピーを108 MHzからEDIDに合う138.5 MHzへ補正し、RGB888/FPDIを設定する。個別機種向けの既存対策で、今回クロック値を新たに発見したわけではない。OmaBoot?の同型機向け資料にも同じパッチと radeon.dpm=0 radeon.pcie_gen2=0 radeon.uvd=0 の併用が記録されている。この3つはchoyer側のマニフェストとLimine項目生成コードでも確認できる。R2もこの組み合わせを使ったが、各引数の効果は個別に検証していない。

採用したHyprland修正：こちらもchoyerのリポジトリ。 Hyprland 0.56.2の元のウィンドウ枠シェーダーに対し、choyerが収録したhyprland/border-alpha.patchを変更せず適用。枠の外を描かない discard を、透明色を出す処理に替える。先行READMEが説明する対象はソフトウェア描画 llvmpipe の枠の乱れ。実機のChromiumのちらつきやGPU停止に効くとは確認していない。

今回の作業：既存修正を、内蔵画面で最初から使えるISOに組み込んだ。 先行手順は標準ISOから外部画面やテキスト端末を使って導入し、修正を適用する流れ。R2では公式カーネルに合うRadeonモジュールとHyprlandを再ビルドして署名し、機種限定のGRUB項目、初期起動イメージ、インストール先へのパッケージ導入、Limine用UKIの再生成をつないだ。モジュールの単体ビルドに合わせたKbuildの調整もこちらの作業で、パネル補正ロジックの変更ではない。ISO再梱包からVM・実機での検証までが今回の作業。R2 は非公式ビルド。Radeon と Hyprland の2件は上記の先行修正を採用し、その後の Chromium 用の2枚はこのプロジェクトで作成・検証した。

Radeonと内蔵画面

標準の起動画面が4分割で重複して見える問題に対し、Omarchy 4.5.0をベースに改修版R2を作成した。対象機種かつ1080pの内蔵パネルに絞り、起動時のパネル設定を補正。クロックを108 MHzから138.5 MHzに変更し、RGB888/FPDIを有効化した。GPUのROMには書き込んでいない。

改修版ではインストーラーが普通に読め、導入後は内蔵画面を1920×1080で使えた。これはこの一台での結果で、他の機種や標準版の動作は示していない。

macOS High Sierra を残して内蔵ディスクを分割

この iMac の内蔵ディスクは 1 TB で、High Sierra は HFS+ に入っていた。既存の HFS+ ボリュームを縮小して Linux 用の空きを作った。GPT の先頭3区画は、もとからある EFI、High Sierra の HFS+、macOS Recovery だった。

R2 のインストーラーでは Free space install を選んだ。初回は外付け USB カードリーダーからルートイメージを展開する途中で停止。この時点で High Sierra が起動することを確認した。内蔵ディスクには、Omarchy 用の EFI（FAT、2 GiB）と暗号化ルート（LUKS、463 GiB）が残った。

再試行前に GPT の変更を予行し、この個体の sda4 と sda5 だけを片付ければ、macOS 側の sda1〜sda3 を保持して連続した 465.1 GiB の空きができることを確認した。この2区画だけを片付け、内蔵 SD スロットから再度 Free space install を実行。導入した Omarchy が起動し、Wi-Fi も使えた。最終インストール後に High Sierra をもう一度起動する試験は未確認。

同じSD、違うリーダー

外付けUSB SDリーダーでは、書き込み後の検証や一部の読み出しで一致しても、iMacのインストーラーで圧縮イメージの読み出し・展開に失敗した。同じSDカードをiMacの内蔵スロットに移すと zstd -t が通り、インストールも完了した。外付け経路のどこに原因があったかは未特定。

外付けリーダーでもカード先頭の ISO 全体を読み出した SHA-256 は一致したが、中の圧縮ルートイメージを繰り返し読むとハッシュが変わった。同じ 15.8 GB の SD カードを内蔵スロットに移すと、展開検査は4分39秒で通った。

電源投入からログイン画面まで

当初、電源投入後のパスワード入力は LUKS のディスク解除用で、その後 SDDM が自動ログインしていた。導入後は本体に解除鍵を置き、ディスクを自動解除して通常の SDDM ログイン画面で待つ設定に変更した。手動解除用の起動項目も残した。本体に鍵を置くため、盗難時のディスク保護は弱まる。

再起動後、暗号化ルートのマウント、ユーザーログイン前の SSH 接続、SDDM のログイン画面プロセスの起動、内蔵パネルの 1920×1080 を遠隔で確認した。この試験での画面の目視とキー入力は未確認。管理用 Mac との双方向 SSH と、ほかの複数の管理機への接続も確認した。設定した接続先の一部は認証試験が残っている。

Chromiumの描き残し

Chromiumでスクロールすると、ちらつきや黒い描き残しが出た。Hyprlandで画面全体を描き直す比較では目立った変化がなく、元に戻した。

Chromiumだけ ~/.config/chromium-flags.conf に --disable-gpu を1行足し、完全終了後に開き直すと、実機でちらつきが消えた。戻すにはその1行を消して開き直す。これはChromiumで効いた回避策で、他のアプリや根本原因は未確認。

別プロファイルでGPU無効化を外し、XWayland経由で試したところ、テスト中にRadeonの描画キュー（ring 0）が停止し、ドライバによるGPUリセットの直後にHyprlandがクラッシュした。セーフモードからいったんログイン画面に戻り、再ログインで通常のデスクトップに復帰。OSは再起動しておらず、この時点では普段のChromiumはGPU無効のままだった。試した経路は再実行しない。根本原因と動画の改善効果は未確認。

動画のデコードは画面描画とは別。Radeonの機能表では、RV730の動画デコーダーはH.264/AVCに対応するが、VP9やAV1には対応しない。現在の起動設定では動画デコーダーも無効にしている。

11月24日のWaylandネイティブでの追試。 一時プロファイルでGPU合成を有効にすると、スクロールに加え、背景色を変えるだけでも古い画素が残った。Waylandに共有バッファ（DMA-BUF）を渡す直前に、追跡した3枚の測定位置を読んだところ、7回すべてで前の色を確認した。画面上の縦1列の587画素は、変更の約0.7秒後に全画素が期待色と異なり、約2.6秒後にすべて一致した。途中の画素取得を省いた試験でも約2.6秒後には一致したが、初期表示の乱れは同じ時点にも残った。

部分更新を全体更新に置き換えても、共有バッファの書き込み完了を示す取得可能なフェンスを待っても、乱れは残った。この時点では Chromium・Mesa・Hyprland のどこで問題が起きるかを特定できなかった。

GPU合成だけを止めた対照試験。 一時プロファイルで --disable-gpu-compositing を指定すると、比較した8画面すべてが期待色と一致し、WebGLは有効だった。普段使いのChromiumの設定はチェックサムで維持を確認。試験導入したGoogle Chrome 158は本体とランチャーを削除し、閲覧データは保存した。

途中ではウェブページにごく薄いアニメーションを重ね、GPU 合成を続けさせる方法も試した。背景色変更とスクロールの計16画面で、125 ms 後の測定位置は期待色に一致した。内部ページには効かず、その後は下記のソース修正に移った。

11月25日の Readback 試験版。 Chromium 155.0.8059.84 に、GL の合成結果を同期的に読み戻し、Wayland に共有メモリ（wl_shm）で渡す経路を追加した。フレームの表示に使う DMA-BUF の取り込み経路を回避する。機能の既定はオフで、比較には --enable-features=WaylandGLReadbackPresentation を使う。

最初のパッチで共有メモリ経由の表示を選べるようになったが、この Radeon では EGL が読み戻し用の画面外バッファを作れなかった。2枚目で Readback 時のバッファに Mesa の surfaceless EGL を使うようにした。2枚を順に適用したものが Readback v2。

実機のネイティブ Wayland では AMD RV730 / ANGLE OpenGL で GPU 合成と WebGL が有効になり、ウィンドウサイズの wl_shm バッファを確認した。試験中の GPU プロセスクラッシュは0回。静止2ページを各3回、さらにスクロール8位置でブラウザーの画像と実画面を比較し、しきい値5%での差はポインター領域だけだった。背景の縦587画素は8位置すべてで初回も安定後も一致した。

Readback v2 を既定の Chromium にし、配布版を削除した後も、アプリメニュー、端末、xdg-open で開くリンク、Omarchy のウェブアプリから修正版が起動することを確認した。比較用の起動項目は撤去し、このユーザー領域の修正版は手動更新としている。

Core 2 Duo での H.264 動画再生

UVD を無効にした起動で、同じ 1080p・30fps の H.264 クリップを mpv で2回 CPU 復号した。CPU 使用率は1コア換算で 58.8% と 59.9%、コマ落ちはどちらも0。ハードウェア復号を指定するとプレーヤーは VA-API 使用と表示したが、Radeon は復号要求を拒否した。

UVD を有効にした試験起動では、標準の Mesa で H.264 を復号できたものの、映像に色の乱れが出た。Mesa 26.2.5 の試験用ドライバーで、圧縮データを Radeon のビデオメモリに置き、復号終了時の同期処理を修正した。システムにインストールした Mesa はそのまま使い、試験プロセスだけに修正版を読み込ませた。

同じ18秒の 1080p30 動画を使い、各コマの時刻・サイズ・画素ハッシュを CPU 復号と比較した。修正版でビデオメモリ入力をオン→オフ→オンにすると、540コマ中の一致数は 540 → 12 → 540 だった。表示を省いた復号試験では、CPU 時間は約4.88秒から0.47〜0.64秒に減った。一方、各コマの完了を待つ測定の実時間は約2.66秒から9.45〜9.62秒に延びた。

画面に表示すると結果は違った。mpv で表示を640×360以下にそろえた2回ずつの試験では、CPU 復号時の CPU 使用率は1コア換算で 65.4%・69.1%、GPU で復号した画像をメインメモリにコピーする方式では 68.0%・68.7% だった。GPU から直接表示する方式は短時間なら動き、CPU 再生と比べた3場面で目立つ崩れはなかった。

続く全編の比較中に画面が固まり、持ち主が電源を切って再起動した。最後に残ったのはコピー経由の試行開始時の空ログで、直接表示の全編測定に入った記録はない。その再起動では通常設定の radeon.uvd=0 に戻った。停止原因と連続再生の安定性は未確認。

11月27日、4.6 RC1 の実機で radeon.uvd=1 を一度の起動に限って有効にし、試作 Mesa ドライバーを使って FFmpeg の VA-API でローカルの 1080p30 H.264 を復号した。全60フレームの画素ハッシュが CPU 参照と一致し、復号エラーは0件だった。復号から読み戻しまでの実時間は約1.65秒。

既存の Chromium Readback v2 は H.264 を無効にしてビルドされており、同じクリップを開くと対応ストリームなしで止まった。H.264 対応の候補版を別にビルド中。Chromium や YouTube でのハードウェア復号と再生性能は未確認。

4.6 RC1 に向けたカーネル試験

11月27日、Omarchy 4.5 の既定起動を保ったまま、内蔵ディスクの Limine メニューに 7.3.6-1-omarchy の試験項目を追加した。4.6 RC1 と同じカーネルに、iMac のパネル用 Radeon 修正を組み合わせた。試験用の SD は作らず、仮想マシンで通常カーネルへの復帰を確認してから実機で試した。 Omarchy 4.6 RC1 リリースノート

実機の初回試験は緊急モードで止まった。通常起動時に、パッケージ管理外の試験モジュールが整理処理で退避されていた。試験用の Radeon は起動イメージに入っていた。起動後に必要な VFAT と Netfilter のモジュールが見つからず、/boot のマウントとファイアウォールが失敗した。

試験カーネルのモジュール一式を署名付きの独立した pacman パッケージにした。既定の 4.5 を先に起動する順序でも消えないことを仮想マシンで再確認。実機の再試験では /boot、ファイアウォール、SDDM が正常に起動し、Hyprland が内蔵パネルを 1920×1080 で使った。描画ログは AMD RV730。画面の枠と長時間の安定性は引き続き検証する。

この実機試験で使ったデスクトップは Omarchy 4.5。別に暗号化済みの 4.5 仮想ディスクを複製し、4.6 RC1 へ上書きした。公式リポジトリから本体とカーネルを、ビルド機の署名付きリポジトリから iMac 用 Radeon と枠修正版 Hyprland を導入した。

仮想マシンは暗号化ディスクを自動解除して SDDM のログイン画面まで進んだ。ログイン後に Foot を開き、別のワークスペースと画面内へ動かせた。その後、Limine の保存スナップショットから 4.5 を起動して復元を実行し、旧カーネル 7.2.15-1-omarchy と Hyprland が通常起動に戻ることを確認した。

実機でも、4.5 の復帰用スナップショットとホームの読み取り専用スナップショットを作り、内蔵ディスク上で 4.6.0rc1-2 と iMac 用の修正パッケージを導入した。設定移行を終え、通常起動用の新しい UKI にカーネル、修正版 Radeon、自動解除用ファイルが入っていることを照合した。

再起動後に SSH で RC1 とカーネル 7.3.6-1-omarchy を確認した。暗号化ディスクが自動解除され、ファイアウォールと SDDM が起動した。ログイン後の内蔵画面にはデスクトップと Omarchy のバーが表示された。Hyprland は内蔵 LVDS-1 を 1920×1080 で使用し、描画ログが Radeon の AMD RV730 を報告した。Limine に 4.5 の復帰項目も残った。

SSH で更新したときに Chrome への切り替え案内を表示できず、その地点から後の設定移行が保留された。RC1 のデスクトップにログインしてから残り14件を適用し、移行の残件が0件、既定ブラウザーが Chromium であることを確認した。実機で検証用の Foot を開き、ウィンドウを画面内で移動できた。枠の目視と長時間の安定性は引き続き確認する。

実機の設定と開発環境

画面は無操作5分でロックして消灯する設定にし、アニメーションのスクリーンセーバーは無効にした。マウスを左下隅に約1秒置いてもロックし、そのまま待つと左下に置いてから約7秒で消灯した。復帰時のパスワード認証も確認した。

zsh 5.9.2をソースからビルドしてユーザー領域に入れ、Footの起動シェルに指定した。標準の ホスト名% プロンプトが出ることを確認した。11月27日には SSH の対話セッションも同じ zsh を起動するようにした。

Git、GCC/G++、Make、Python、Node.js、npm、pnpm、Deno、Ruby、Neovimのバージョンを確認した。Docker CLIは確認済みで、コンテナの起動は未検証。

ビルド中の CPU・メモリ使用量は btop で確認できた。音声入力用の Superwhisper はクラウド処理に設定され、Option＋Space に割り当てられていた。

Codex CLIとデスクトップアプリ

OmarchyのAgentsからCodex CLIを起動。2009年iMacの内蔵Bluetoothは2.1で、iPhoneでQRを読む方式に必要なBLEを備えていない。CLIの「Sign in with Device Code」を選び、iPhoneのブラウザで認証を完了できた。これはiMac側のデスクトップアプリやブラウザへのログインを兼ねない。

ブラウザ版ChatGPTでは、iPhoneでQRコードを読んでもパスキー認証が先に進まなかった。この iMac の内蔵 Bluetooth は、スマートフォンとの近接確認に使う BLE に対応していない。

USB-C の YubiKey を変換アダプタで iMac の USB-A 端子につなぎ、Omarchy 上で Google アカウントにログインできた。同じ YubiKey でブラウザ版 ChatGPT にもログインできた。

デスクトップ版の導入。 この記録を担当するCodexが、OpenAI公式のArch Linux向けパッケージ 26.1120.41243 の署名とSHA-256を照合した。インストーラーとパッケージの設定フックは実行せず、本体をユーザー領域へ展開。システム更新を伴わない配置で、アプリは手動で更新する。 公式Linuxガイド

アプリ一覧では ChatGPT (Codex)、端末では chatgpt で起動できる。内蔵Radeon向けにランチャーで --ozone-platform=wayland --disable-gpu を指定し、サインインに使う codex: リンクをユーザー単位で登録した。

Core 2 Duo E7600の実機では、一時プロファイルを使ったヘッドレス起動で、サインイン画面の初期化とローカルのCodexサーバーへの接続をログで確認した。

11月24日、iMac上のCodexデスクトップのチャットから実機のコマンドを実行し、GUIを使った検証も行えた。この作業では新規サインインの手順は確認していない。

11月27日、署名を検証した公式パッケージから 26.1120.50957 に更新した。ログイン情報とデータを引き継いで Wayland ウィンドウが開き、以前の Codex タスクから実機コマンドを実行できた。次回も端末から chatgpt-update --check で確認し、chatgpt-update でアプリを入れ替えて再起動できるようにした。

Codex デスクトップアプリが同梱する描画エンジン Owl でも GPU 合成を試した。強いちらつきが現れ、XWayland の試験では GPU プロセスが一度異常終了したため、試験を終了してアプリは GPU 無効設定に戻した。上流 Chromium 158 へのパッチ移植は適用確認までで、Owl の修正版ビルドや描画成功の記録はない。

パッチとビルド設定

1. Chromium 155.0.8059.84 用の Wayland Readback パッチ · 2. EGL バッファの修正 · SHA-256 · GN 設定 · 固定した Chromium ソース

対象は Ozone Wayland を使う Linux x86_64。確認対象の iMac は Core 2 Duo E7600 と Radeon HD 4670 を搭載する。フレームごとに同期読み戻しが入るため、実機での性能は別に評価する。

Radeon のパネル補正と Hyprland の枠シェーダー修正は先行プロジェクトの成果。採用した版と出典は「修正の出自と、今回作った部分」に記載した。

Linux x86_64 版の全体ビルドは Apple Silicon 上の amd64 Docker で行い、最初は QEMU、途中から Rosetta を使った。iMac 自体でも初版の修正対象2本をコンパイルできた。実機側の全体ビルドは 53,356 工程中 16,910 で停止。実機で描画を確認した本体は Apple Silicon 側のビルドで、既存の生成物を使った v2 の差分ビルドはリンクまで約51秒だった。
