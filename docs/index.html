HARDWARE REPORT · UPDATED FRI, NOV 27, 2026

Omarchy on a 2009 iMac

Booting the stock Omarchy 4.5.0 installer on a Late 2009 iMac produced a corrupted display: four copies of the same splash appeared in a 2×2 grid. I built a custom ISO with a Radeon fix while preserving the official boot layout. The photos show the stock boot splash and the desktop after installation from R2. The iMac later ran 4.6 RC1, where we tested Radeon video decoding in Chromium and measured YouTube playback.

Nov 23 · Installation and first boot

Radeon and the built-in display

The stock boot display was duplicated into four tiles. The modified R2 image was built from Omarchy 4.5.0 and corrects panel settings in memory, only for the matching model and 1080p internal panel. It changes the panel clock from 108 MHz to 138.5 MHz and enables RGB888/FPDI. The GPU ROM was not flashed.

The installer became readable, and the installed system used the built-in display at 1920×1080. This result is for one machine and does not establish support for other models or the unmodified image.

How the custom installer ISO was built

1. Start from the official ISO. After checking the official signature and published SHA-256 for omarchy-4.5.0-x86.iso, I opened the ISO and its live SquashFS read-only. The original linux-omarchy 7.2.15-1 kernel was retained. This was not a full OS rebuild.

2. Build only the x86_64 components on Apple Silicon. Colima supplied a Linux VM, and QEMU CPU emulation ran a Docker linux/amd64 Arch container. Using signature-verified headers for the official kernel and matching GCC 16.2.1, I rebuilt only the radeon.ko module with the built-in panel timing fix. The module’s compatibility metadata and dependencies were checked before packaging it as omarchy-imac10-1-radeon 7.2.15-1. For Hyprland, I used the Arch build recipe and changed the window-border shader from discard to an alpha-zero output; that narrow patch became 0.56.2-4.1. Both packages were signed with a separate local key, not the official signing key.

3. Apply the fixes both live and after installation. GRUB gained a dedicated entry shown only on iMac10,1, which boots the patched live Radeon module and an initramfs built with mkinitcpio. On that path, package signatures are checked before partitioning. During installation, a temporary scoped keyring and pacman -U install the patched packages, and the module lookup order is checked. The stock prebuilt unified kernel image (UKI) is discarded so the normal Limine-oriented flow generates a new one. The official install payload omarchy-root.img.zst remains unchanged.

4. Repack without replacing the official boot layout. I rebuilt live airootfs.sfs with mksquashfs and Zstandard compression, then regenerated its SHA-512 sidecar. xorriso -boot_image any replay retained the original ISO’s boot layout while replacing the GRUB configuration, initramfs, SquashFS, and checksum.

5. Verify the VM, then test physical hardware. The stock ISO reached the installer in a VM. The Radeon-only R1 smoke test uncovered an installer path-check issue, which was fixed in R2. I remounted R2 to check the byte-identical kernel, patched module, hashes, and signatures. A UEFI VM with a Core 2 Duo-class CPU and 4 GB RAM completed an encrypted install, booted with the virtual installer detached, and had the installed UKI verified. The VM used software llvmpipe, so it did not validate the physical Radeon display or Wi-Fi. In the installed VM session we opened Foot and moved its window across workspaces and to new coordinates.

Making room for Omarchy alongside macOS High Sierra

The iMac had a 1 TB internal disk with High Sierra on HFS+. We shrank the existing HFS+ volume to make room for Linux. The GPT entries for the original EFI partition, the HFS+ system volume and macOS Recovery occupied the first three slots.

In the R2 installer we chose Free space install. The first attempt stopped while extracting the root image from an external USB card reader. High Sierra still booted at that point. The interrupted install had left two additional partitions on this disk: a 2 GiB FAT EFI partition for Omarchy and a 463 GiB LUKS root partition.

Before retrying, a GPT dry run showed that removing only those two new partitions (sda4 and sda5 on this machine) would preserve sda1–sda3 and yield 465.1 GiB of contiguous free space. We cleared those two partitions and ran Free space install again from the built-in SD slot. The installed Omarchy booted and Wi-Fi worked. A High Sierra boot after this final installation is still unverified.

Same SD card, different reader

With an external USB SD reader, the iMac installer failed to read or decompress the image even though write verification and some readbacks matched. Moving the same card to the built-in SD slot passed zstd -t and the installation finished. The exact fault in the external path was not isolated.

Readback of the entire ISO matched its SHA-256 even on the external reader. Repeated reads of the compressed root image gave different hashes there. In the built-in slot, the same 15.8 GB card passed the decompression check in 4 min 39 s.

Chromium redraw artifacts

Scrolling in Chromium produced flicker and black regions that failed to redraw. A temporary Hyprland test that repainted the whole display made little visible difference and was reverted.

Adding --disable-gpu as one line in ~/.config/chromium-flags.conf, then fully quitting and reopening Chromium, stopped the flicker on this machine. To undo it, delete that line and reopen Chromium. This is an app-specific workaround, not a diagnosis of the root cause or a confirmed fix for other apps.

In a separate profile, the GPU-disable flag was omitted and Chromium ran through XWayland. During that test, Radeon’s graphics queue (ring 0) stalled. The driver reset the GPU, and Hyprland then crashed. After exiting Safe Mode to the login screen and signing in again, the normal desktop returned without rebooting Linux. At that stage the regular Chromium profile still started with the GPU disabled. This test should not be repeated as-is. The root cause and any playback benefit are unverified.

Video decoding is separate from rendering. The Radeon feature table lists H.264/AVC support on the RV730 video decoder, but not VP9 or AV1. That decoder is disabled in this build’s boot settings.

Signing in to Codex CLI

Codex CLI was launched from Omarchy’s Agents panel. The 2009 iMac’s built-in Bluetooth 2.1 lacks the BLE required by the phone-based passkey QR flow. Choosing “Sign in with Device Code” and completing authorization in the iPhone browser worked for the CLI. It did not sign in the iMac’s browser or desktop app.

In the iMac’s browser, the ChatGPT passkey sign-in did not progress after I scanned the QR code with my iPhone. The built-in Bluetooth hardware lacks BLE for the phone proximity check.

Nov 24 · Sign-in and rendering

From power-on to the login screen

Initially the password prompt at startup unlocked LUKS, then SDDM automatically logged in the user. After installation we changed this machine to unlock the disk automatically and wait for a password at the SDDM login screen. A manual disk-unlock boot entry was retained. Keeping an unlock key on the boot disk reduces protection if the machine is stolen.

After a reboot, SSH confirmed that the encrypted root was mounted, SDDM had started its greeter before user login, and the internal panel reported 1920×1080. This check was remote. We also verified two-way SSH login with a management Mac and outbound login to several other hosts. Some configured destinations still awaited an authentication test.

Installing the Codex desktop app

Desktop installation. The Codex task maintaining this record verified the signature and SHA-256 of OpenAI’s official Arch Linux package, version 26.1120.41243. The app was extracted into user space, without running the installer or package hooks. This avoided a system upgrade. App updates are manual. Official Linux guide

Open ChatGPT (Codex) from the app menu or run chatgpt in a terminal. The launcher passes --ozone-platform=wayland --disable-gpu for the built-in Radeon. The codex: sign-in link was registered for the current user.

On the Core 2 Duo E7600 iMac, a headless run with a temporary profile initialized the sign-in screen and connected to the local Codex server, as confirmed in the app logs.

On Nov 24, a chat in the Codex desktop app on the iMac ran commands and carried out GUI checks. This work did not directly test a fresh sign-in.

Desktop settings and development tools

The screen now locks and blanks after five idle minutes, with the animated screensaver disabled. Holding the pointer in the bottom-left corner for about a second also locks the session. The display blanked about seven seconds after moving the pointer there. Password authentication on return was verified.

zsh 5.9.2 was built from source in user space and selected as Foot’s startup shell. The standard hostname% prompt appeared.

Versions were checked for Git, GCC/G++, Make, Python, Node.js, npm, pnpm, Deno, Ruby, and Neovim. The Docker CLI was present. Starting a container has yet to be tested.

The iMac also had btop for observing CPU and memory during builds. Superwhisper was configured for cloud processing and bound to Option–Space for dictation.

Tracing stale frames on Wayland

Nov 24 follow-up on native Wayland. With GPU compositing enabled in a temporary profile, changing the background color alone reproduced the stale pixels. In all seven color changes, the sampled location in each of three tracked DMA-BUFs still held the previous color just before handoff to Wayland. Of 587 pixels in a vertical column on the display, all differed from the expected color after about 0.7 seconds and all matched after about 2.6 seconds. The later sample still matched when the intermediate capture was skipped. Artifacts in the initial frame persisted at the same sampling time.

Replacing partial damage with full updates and waiting on the available write-completion fences each left artifacts. Those tests did not locate the cause in Chromium, Mesa, or Hyprland.

Control with GPU compositing disabled. In a temporary profile with --disable-gpu-compositing, all eight compared frames matched the expected color, and WebGL remained available. Checksums confirmed that the regular Chromium configuration was preserved. The trial Google Chrome 158 installation and launcher were removed, and browsing data was kept.

An interim launcher kept GPU compositing active by animating a nearly transparent overlay on web pages. All 16 sampled background or scroll states showed the expected color at 125 ms, but this workaround did not cover internal browser pages. The source patches below replaced this experiment.

Nov 25 · Browser and video

Making Chromium Readback v2 the default

Nov 25 Readback test build. Chromium 155.0.8059.84 gained an optional path that synchronously reads back the composited GL frame and hands it to Wayland in shared memory (wl_shm). This bypasses the DMA-BUF import path used for presentation. The feature defaults to off. Enable it with --enable-features=WaylandGLReadbackPresentation for comparisons.

The first source patch selected shared-memory presentation. Its EGL configuration could not create the offscreen buffer needed for hardware readback on this Radeon. The second patch selects Mesa’s surfaceless EGL platform for that buffer on the Readback path. Both patches, applied in order, make up Readback v2.

On native Wayland, the iMac reported AMD RV730 through ANGLE OpenGL with GPU compositing and WebGL enabled. The test observed window-sized wl_shm buffers and zero GPU-process crashes. Two static pages tested three times each and eight scroll positions matched the browser capture outside the pointer area at the 5% comparison threshold. At all eight positions, the 587-pixel background sample line matched both initially and after settling.

Readback v2 became the default Chromium. After removing the distribution package, the app menu, terminal command, links opened with xdg-open, and Omarchy web apps used the patched build. The comparison launcher was retired. This user-local build is updated manually.

Browser sign-in with a YubiKey

I connected my USB-C YubiKey to the iMac’s USB-A port with an adapter and signed in to my Google account on Omarchy. I also used the same YubiKey to sign in to ChatGPT in the browser.

GPU compositing in the Codex app

A separate test enabled GPU compositing in the ChatGPT desktop app, which uses the bundled Owl engine. Visible flicker returned and an XWayland trial recorded a GPU-process crash. We ended the trial and kept GPU rendering disabled for this app. A port of the patches applied to upstream Chromium 158 source, but no patched Owl build or successful Owl rendering test was recorded.

H.264 decoding tests

With UVD disabled at boot, the same 1080p30 H.264 clip played twice in mpv using CPU decoding. CPU use was 58.8% and 59.9% of one core, with zero dropped frames in both runs. When hardware decoding was requested, the player reported VA-API but Radeon rejected the decode request.

On a test boot with UVD enabled, stock Mesa decoded H.264 but produced visibly corrupted frames. An experimental Mesa 26.2.5 driver placed the compressed input in Radeon video memory and fixed synchronization at decoder teardown. Only the test processes loaded this driver.

For the same 18-second 1080p30 clip, we compared timestamps, sizes and pixel hashes against CPU decoding. With video-memory input switched on, off and on again in the patched driver, 540, 12 and 540 of the 540 frames matched. In a decode-only test, process CPU time fell from about 4.88 s to 0.47–0.64 s. Elapsed time increased from about 2.66 s to 9.45–9.62 s when the test waited for each hardware-decoded frame.

Displaying the video changed the result. With mpv output limited to 640×360, CPU decoding used 65.4% and 69.1% of one core in two runs. Hardware decoding with frames copied back to system memory used 68.0% and 68.7%. Direct GPU presentation worked in a short trial. Three displayed scenes showed no obvious corruption when compared with CPU playback.

The owner reported a freeze during the subsequent full-length comparison and powered the iMac off. The last file was an empty log from the start of the copy-back run. There was no record of the full-length direct-presentation run starting. The iMac rebooted with its usual radeon.uvd=0 setting. The freeze’s cause and sustained playback stability remain open.

Immediately after this reboot, Linux did not detect the USB optical mouse and Hyprland listed no mice. The kernel detected the same mouse again at 12:07 JST, and it was still registered as an input device that evening. Pointer movement on screen has yet to be confirmed.

After installing RC1, we tested GPU decoding in Chromium and YouTube.

Nov 27 · RC1 and YouTube

Updating the Codex desktop app

On Nov 27, we updated the app to 26.1120.50957 from a signature-verified official package. The updated app kept the sign-in and user data, opened a Wayland window, and ran commands in the existing Codex task. From a separate terminal, chatgpt-update --check checks the installed version against the official package and chatgpt-update replaces and relaunches the app.

Trying the new kernel in Limine

On Nov 27, we added 7.3.6-1-omarchy as a separate entry in Limine on the internal drive, keeping the existing Omarchy 4.5 boot as the default. The trial used the kernel shipped with 4.6 RC1 and the iMac’s Radeon panel fix. We verified that the VM could return to the original kernel before trying the iMac, without making a trial SD card. Omarchy 4.6 RC1 release notes

The first iMac trial stopped in emergency mode. During an earlier normal boot, a cleanup service moved the trial’s module tree because it had no owner in pacman. The trial image already contained Radeon. Once userspace started, missing VFAT and Netfilter modules blocked the /boot mount and firewall startup.

We put the entire trial module tree in a separate signed pacman package. In the VM, the modules survived when we booted the default 4.5 entry first. On the next iMac trial, /boot mounted and the firewall and SDDM started. Hyprland drove the built-in panel at 1920×1080, and its renderer log identified AMD RV730. Window borders and long-term stability still need separate checks.

The kernel trial was followed by the in-place upgrade to 4.6 RC1.

Using the same zsh in Foot and SSH

Interactive SSH logins now start the same user-installed zsh 5.9.2 as Foot.

Upgrading from 4.5 to 4.6 RC1

The Limine kernel trial used the Omarchy 4.5 desktop. In a separate test, we cloned the encrypted 4.5 VM disk and upgraded it in place to 4.6 RC1. The official repositories supplied Omarchy and the kernel. A signed repository on the build host supplied the iMac’s Radeon module and Hyprland border patch.

The upgraded VM unlocked its encrypted disk automatically and reached the SDDM sign-in screen. After signing in, we opened Foot and moved it to another workspace and across the screen. We then booted the saved Limine snapshot, restored it, and verified that the old 7.2.15-1-omarchy kernel and Hyprland started from the normal boot entry.

On the iMac, we saved a 4.5 recovery snapshot and a read-only snapshot of the home volume, then installed 4.6.0rc1-2 and the iMac packages on the internal drive. After the settings migration, we verified the kernel, patched Radeon module, and automatic unlock files in the UKI for the normal boot entry.

After rebooting, SSH confirmed RC1 and kernel 7.3.6-1-omarchy. The encrypted disk unlocked automatically, and the firewall and SDDM started. The iMac’s panel showed the desktop and Omarchy bar after sign-in. Hyprland drove the built-in LVDS-1 at 1920×1080, and its renderer log identified the Radeon as AMD RV730. The 4.5 recovery entry remained in Limine.

The SSH update paused the settings migrations at the optional Chrome offer, which needs the desktop to display it. After signing in to RC1, we ran the remaining 14 migrations and verified that none were pending. Chromium was still the default browser. We opened a Foot terminal on the iMac and verified that its window could move across the display. Visual inspection of window borders and long-term stability are still pending.

YouTube GPU playback and CPU load

On Nov 27, one trial boot of 4.6 RC1 enabled radeon.uvd=1. FFmpeg decoded a local 1080p30 H.264 clip through Radeon VA-API with the experimental Mesa driver. All 60 frames matched the CPU reference hashes, with zero decode errors. Decoding and reading the frames back took about 1.65 seconds.

The installed Chromium Readback v2 was built with H.264 disabled and reported no supported streams for the same clip.

On Nov 27, we built a Chromium candidate with H.264 enabled. The first build selected Radeon’s VaapiVideoDecoder but stopped after four frames when Chromium could not import the decoded frame as a shared image. The next revision restored frame import and kept Wayland shared-memory presentation for the flicker workaround.

The revised build played all 60 frames of a local 1080p30 H.264 clip without drops. YouTube initially chose AV1. We added a setting that reports H.264 as the only supported video codec in the test profile. YouTube then used Radeon to decode 240p H.264 for about 8.2 seconds and rendered 195 frames with zero drops.

With the panel blanked and the same YouTube video fixed to 480p H.264, the Chromium processes used 45.3% CPU with software decoding and 46.3% with Radeon decoding. Neither run dropped frames in the roughly 20-second sample. Later instrumentation showed that the browser did not read back frames during playback with the panel off. All CPU percentages here use both cores as 100%.

With the panel on and a local 720p24 clip playing, CPU use on the video-processing thread fell from 6.7% with software decoding to 0.7% with Radeon. In the same 1600×940 window, total Chromium CPU fell from about 56% to 55%. Reducing the window to 960×650 brought Chromium CPU to about 36% with Radeon and the same source clip.

We kept the 1600×940 window and tried reading back only the changed area. In two roughly 10-second samples of the local 720p clip, partial readback cut CPU time in the readback call from 0.73 s to 0.28 s, transferred data from 1.27 GB to 0.49 GB, and dropped frames from 28 to 7. All 283 frames checked in a separate validation matched the full-frame reference pixel for pixel. Visual inspection of the panel and long-run stability are still pending.

With the panel on, the partial-readback build used Radeon for YouTube at 720p H.264. It dropped 51 of 372 frames in about 15.6 seconds. The iMac used about 98% CPU, with about 32% on Chromium’s renderer main thread alone. The full-frame readback control exited before a matched sample could be collected. These measurements used a test build and a temporary browser profile. Big Buck Bunny, the test video

In November 2009, YouTube listed 360p as standard quality, 480p as high quality and 720p as HD. It added 1080p that month. In December, YouTube tested a lighter watch page called Feather that defaulted to standard quality and reduced features such as comments. The experimental HTML5 player for Safari followed in January 2010. Smooth standard-quality playback on a Mac of the time is plausible. We have yet to measure playback on this model using its original Mac OS X setup. 2009 quality announcement · Feather announcement · HTML5 player announcement

Patches, sources and revisions

Patch provenance and what this project added

Base: official Omarchy. The boot media is based on the official Omarchy 4.5.0 x86 release. For the installer, two matching file hashes tied the relevant files in the image to the reference omarchy-iso source; the reference commit was not read from embedded ISO metadata. The kernel binary and compressed installation payload remain the official files.

Radeon fix adopted from choyer’s repository. The build uses patches/panel-encoder-combined.patch unchanged from reference commit 0d5a406a312eb91c640c6137ef4e90813baa8778. It corrects the in-memory video BIOS panel table for the matching iMac10,1 display, changing 108 MHz to the EDID’s 138.5 MHz and setting RGB888/FPDI. The clock correction was not discovered in this project. OmaBoot?’s entry for the same model documents the same patch and the grouped parameters radeon.dpm=0 radeon.pcie_gen2=0 radeon.uvd=0. The same three settings are in choyer’s manifest and Limine entry writer. R2 uses that combination, but did not test each parameter independently.

Hyprland fix also adopted from choyer’s repository. The hyprland/border-alpha.patch file was applied unchanged to the original Hyprland 0.56.2 window-border shader. It replaces discard outside the border with a transparent output. The earlier README describes its scope as border artifacts under the llvmpipe software renderer. It was not verified as a fix for Chromium flicker or a GPU hang on the physical machine.

This project integrated the existing fixes into an ISO that can start with the built-in screen. The earlier procedure starts with the stock ISO and uses an external display or text terminal to install and apply the fixes. R2 rebuilds and signs packages for the original kernel and matching Hyprland base, then integrates a model-specific GRUB entry, initramfs, installation of the patched packages on the target, and regeneration of the Limine UKI. The Kbuild adjustment for building the module on its own is local build glue, not a change to the panel correction. Repacking and validation in a VM and on the actual iMac are this project’s work. R2 is an unofficial build. The Radeon and Hyprland fixes are credited above. The two later Chromium patches were developed and tested in this project.

Patch and build settings

1. Wayland Readback patch for Chromium 155.0.8059.84 · 2. EGL pbuffer fix · SHA-256 · GN settings · Pinned Chromium source

The build targets Linux x86_64 with Ozone Wayland. The iMac has a Core 2 Duo E7600 and Radeon HD 4670. The YouTube playback measurements include the cost of full-frame readback and an experiment that reads back only changes.

The Radeon panel correction and the Hyprland border shader fix came from an earlier project. The provenance section records the exact revisions used here.

The full Linux x86_64 build ran in an amd64 Docker container on Apple Silicon, initially under QEMU and then Rosetta. On the iMac itself the two changed C++ objects compiled, and the full build stopped at 16,910 of 53,356 actions. The executable tested on the iMac came from the Apple Silicon host. Relinking v2 on that host took about 51 seconds with the previous objects available.
